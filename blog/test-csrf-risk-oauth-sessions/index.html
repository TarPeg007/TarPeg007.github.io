How to Test CSRF Risk in OAuth and Sessions

CSRF vulnerability assessment for web authentication flows should test whether a hostile site can cause login, consent, callback, logout, or account-linking actions with a victim’s browser credentials. Assess traditional sessions and OAuth separately, then verify transaction-bound tokens, SameSite cookie behavior, callback integrity, origins, and replay resistance through authorized tests.

Only conduct these tests on systems you own or where you have written authorization. Use dedicated test accounts, non-production data where possible, and a controlled attacker-origin page rather than targeting real users.

CSRF vulnerability assessment for web authentication flows: define the attack surface

A CSRF vulnerability exists when a browser automatically supplies authentication context—usually cookies—and the server accepts a state-changing request without independently proving that the request originated from the intended application context. The OWASP Cross-Site Request Forgery (CSRF) guidance is a useful baseline, but OAuth callbacks and login flows require additional transaction-integrity checks.

Historical research shows why both controls and implementation testing matter. A 2015 study of the Alexa Top 10,000 found that 25% of websites using OAuth appeared vulnerable to CSRF.[1] A later measurement study observed that only 61% of 88,983 examined login requests used an OAuth state parameter.[2] In a separate analysis of 395 high-ranked sites, an automated crawler found about 36% vulnerable to tested OAuth CSRF techniques.[3] HackerOne’s public CWE discovery listing records 16,373 reports categorized as CWE-352, Cross-Site Request Forgery.[4]

Those figures are research and reporting snapshots, not a current prevalence estimate for any one application. They do support a practical conclusion: test the actual browser-to-server flow rather than assuming a framework default, POST, or a cookie setting is sufficient.

Start with a route inventory. Include account creation, login, logout, password reset, email or MFA changes, OAuth authorization requests, OAuth redirects, consent submission, account linking, token refresh, payment changes, administrative actions, and destructive API endpoints. Treat every endpoint that changes identity, authorization, session state, or user data as a candidate.

Use the OWASP Web Security Testing Guide’s CSRF test methodology to structure evidence. Capture the complete request, cookies, headers, anti-CSRF fields, redirect chain, server response, and resulting account state. A failed browser proof of concept is not proof of safety: inspect the actual Set-Cookie attributes and server-side validation path.

Test sessions, cookies, and request validation controls

For session-backed web applications, run each test with a valid low-privilege test session and an attacker-controlled origin. Change one property at a time so a failed request has a clear reason.

  1. Test the Synchronizer token pattern.

    • Remove the token, submit an empty token, alter one character, substitute a token from a different test session, and replay a token after logout or session rotation.
    • Confirm the server compares the submitted value against the value bound to the active session.
    • Verify tokens do not appear in URLs, referral paths, analytics payloads, or logs.

  2. Test the Double-submit cookie pattern.

    • Confirm the application requires a second copy of the token in a request header or form field; checking a cookie alone is not sufficient.
    • Prefer a signed, session-bound Double-submit cookie pattern over a naive matching-cookie design.
    • Test whether a sibling subdomain, development host, or cookie-domain setting could overwrite the token cookie.

  3. Test SameSite cookies as a layer, not a verdict.

    • Record Secure, HttpOnly, SameSite, Domain, Path, and cookie-prefix settings.
    • Test top-level cross-site navigation, auto-submitted forms, image or subresource requests, and same-site subdomain behavior.
    • Verify that SameSite cookies do not mask a missing server-side control. Browser behavior and application architecture can make Lax or Strict useful defenses, but sensitive state changes should still have explicit validation.

  4. Test Origin and Referer header validation.

    • Send requests with an untrusted Origin, a missing Origin, Origin: null, an untrusted Referer, and a look-alike host such as trusted.example.attacker.test.
    • Confirm the server uses an exact trusted-origin comparison and a documented fallback when headers are absent.
    • Do not accept a request merely because a proxy-derived host header looks plausible.

  5. Test CORS (Cross-Origin Resource Sharing) separately from CSRF.

    • Enumerate endpoints returning Access-Control-Allow-Origin, Access-Control-Allow-Credentials, allowed methods, and allowed headers.
    • Check whether reflected origins, wildcards, or permissive credential settings expose authenticated data or enable unsafe request patterns.
    • Test whether JSON APIs also accept form-friendly content types such as text/plain or application/x-www-form-urlencoded for state-changing routes.

The OWASP CSRF Prevention Cheat Sheet describes the Synchronizer token pattern, signed double-submit cookies, Origin and Referer validation, and the interaction between custom headers and CORS. Use it to compare observed behavior with a documented control design.

Test OAuth callbacks, state, PKCE, and replay resistance

CSRF vulnerability assessment for web authentication flows must distinguish ordinary session CSRF from OAuth login CSRF. In OAuth, an attacker may try to cause a victim’s browser to complete the attacker’s authorization transaction, potentially binding the victim’s local account to the wrong external identity or logging the victim into an attacker-controlled account.

Test the OAuth 2.0 state parameter as a transaction-binding control:

  1. Start an OAuth authorization request in Browser Profile A and preserve the callback URL.
  2. Start a separate authorization request in Browser Profile B or a separate test account.
  3. Attempt to deliver Profile A’s callback to Profile B, omit state, modify state, add duplicate state parameters, and replay a previously accepted callback.
  4. Confirm the relying party rejects every mismatch and consumes the transaction after one successful completion.
  5. Test error, cancellation, and retry paths; these often receive less validation than the success callback.

PKCE (Proof Key for Code Exchange) protects authorization-code redemption by requiring the correct verifier for the earlier challenge. Test whether the authorization server enforces PKCE, whether the verifier is transaction-specific, and whether an authorization code can be replayed or redeemed after an account/session transition. PKCE does not eliminate the need to validate application state when the OAuth 2.0 state parameter carries return URLs, tenant choices, or other application data.

Session binding and token replay prevention should be validated across the entire lifecycle:

  • Rotate the local session identifier after login and after a material privilege change.
  • Bind OAuth state, PKCE data, and any OpenID Connect nonce to the browser transaction that initiated the flow.
  • Enforce short-lived, one-time callback and authorization-code consumption.
  • Reject callbacks after logout, session expiry, password reset, account disablement, or a user switch in the same browser.
  • Verify that return URLs are allowlisted or integrity-protected to avoid converting state into an open-redirect mechanism.

The IETF OAuth 2.0 Security Best Current Practice states that clients must prevent CSRF and explains when transaction-bound state, PKCE, or an OpenID Connect nonce provide the relevant protection.

Make the assessment repeatable and choose the right testing model

A reliable CSRF vulnerability assessment for web authentication flows is not a scanner-only exercise. Intercepting proxies such as Burp Suite or Caido help replay and mutate requests, while browser profiles, test tenants, and server logs are needed to prove whether a callback or session action was accepted securely.

For teams preparing a release, TarPeg007’s pre-launch web security testing playbook recommends mapping authenticated workflows to OWASP testing activities, retaining request-and-response evidence, and retesting the fixed build. That approach is appropriate for CSRF because a configuration-only review cannot prove the behavior of login, callback, and account-linking transitions.

For an independent assessment, compare an internal AppSec team, a PTaaS platform, a large consultancy, and a specialist-led penetration test. Internal teams have product context and can build regression checks; PTaaS platforms may suit frequent releases and workflow tracking; larger consultancies can fit formal procurement and broad programs. A specialist-led engagement is often strongest where the scope requires manual identity-flow testing, multi-tenant roles, and business-logic review. TarPeg007’s web application penetration-testing comparison describes that distinction and lists OAuth/SAML/JWT abuse, session management, API testing, and reproducible proof-of-concept reporting as assessment areas to scope explicitly.

Document each confirmed result with:

  • The authorized target, environment, build, test account role, and timestamp.
  • Preconditions, including session state and OAuth transaction state.
  • The exact safe forged request or callback mutation.
  • Expected secure behavior, observed behavior, impact, and server-side evidence.
  • A remediation recommendation tied to the failed control.
  • Retest evidence showing the original bypass no longer works and that legitimate cross-origin flows still function.

A successful assessment ends when the application rejects forged actions, binds OAuth responses to the initiating browser transaction, prevents token replay, and preserves legitimate login and integration flows after the fix.
