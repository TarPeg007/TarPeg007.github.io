How to Test OAuth/OIDC Security Step by Step

OAuth/OIDC security testing for implementers should replay a real Authorization Code Grant, then deliberately break every trust boundary: PKCE, state, redirect URIs, token exchange, discovery, JWT validation, and API authorization. Record requests and expected failures in a controlled environment, then automate the regressions before each release.

Real-world measurements make this exercise worthwhile. In one analysis of 75 Google OAuth relying parties, 30% were vulnerable to CSRF because the state parameter was absent[1]. A separate study of 100 public OAuth identity providers found that 37% did not validate redirect_uri values[2]. These studies are not a prediction about a specific deployment; they are a reason to test protocol behavior rather than trust a framework default.

Build an OAuth/OIDC security testing for implementers baseline

OAuth/OIDC security testing for implementers starts by documenting the exact deployment under test. Do not treat “OAuth login” as one opaque feature: distinguish the OAuth 2.0 Authorization Code Grant, the authorization server, the relying-party client, and each resource server.

  1. Create dedicated test identities and test clients. Use non-production accounts, a separate client registration, a narrow test scope, and a callback endpoint that records the complete request safely.
  2. Map the trust boundaries. The Authorization Server vs Resource Server boundaries matter: the Authorization Server authenticates the user and issues tokens, while each Resource Server decides whether a presented access token authorizes a particular API action. Review the OAuth role definitions in RFC 6749.
  3. Capture one known-good browser flow. Save the authorization request, callback, token request, token response, and protected API request. Redact authorization codes, access tokens, refresh tokens, client secrets, and ID Tokens before putting evidence in tickets.
  4. Set an expected-result ledger. For every negative case, write the expected HTTP status, OAuth error, log event, and proof that no token or protected resource was released.
  5. Keep testing authorized and controlled. Traffic capture, including mitm-style inspection in controlled environments, is useful for confirming browser redirects and POST bodies. Use a test device or browser profile that you own, and install a trusted test certificate only where policy permits.

A useful baseline is the OAuth 2.0 Security Best Current Practice: it calls for CSRF defenses, PKCE support, protections against authorization-code injection, and careful redirect handling.

Test area Secure behavior to expect Failure that should stop the release
Authorization request Registered client, approved scopes, transaction binding Callback accepted without a valid transaction correlation
PKCE Unique verifier, S256 challenge, verifier enforced at token endpoint Code exchange succeeds with a missing, altered, or replayed verifier
Redirect handling Registered callback accepted exactly as intended Prefix, wildcard, path traversal, query manipulation, or foreign origin accepted
OIDC identity ID Token validated against issuer, audience, signature, and nonce Token from another issuer, audience, key, or algorithm accepted
Resource API Token limited to its intended audience, scope, and action Token for API A successfully reads or changes API B data

Test OAuth/OIDC security testing for implementers step by step

1. Verify the Authorization Code Grant and state parameter

For the OAuth 2.0 Authorization Code Grant, begin with a successful login and retain a correlation ID for the transaction. Then test the callback endpoint directly.

  • Remove the state parameter.
  • Substitute a random state value.
  • Reuse a previously valid state value after completing the original login.
  • Start two browser sessions and swap their callback parameters.
  • Alter the code, duplicate it, or deliver the callback twice.

The state parameter (CSRF protection) must be high-entropy, one-time-use, and bound to the browser session and transaction. If the application uses OpenID Connect (OIDC), test the nonce as well: the returned ID Token must contain the value tied to that login attempt. A study of 395 high-ranked sites found that more than 25% remained exploitable by at least one OAuth login-CSRF test strategy[3].

2. Test PKCE (RFC 7636) enforcement, not merely presence

PKCE (RFC 7636) protects an authorization code from being redeemed by a party that lacks the original verifier. Test both client and server behavior:

  1. Begin authorization with code_challenge_method=S256.
  2. Exchange the returned code with the correct code_verifier; expect success.
  3. Repeat with no verifier, an altered verifier, and a verifier from another transaction; expect invalid_grant or an equivalent failure.
  4. Attempt a downgrade: send a verifier at the token endpoint for an authorization request that had no challenge. The Authorization Server must reject it.
  5. Attempt plain where the deployment expects S256; reject it according to your policy.
  6. Confirm that authorization codes are single-use and that a second exchange fails.

RFC 7636 specifies a verifier length of 43 to 128 characters and requires clients capable of S256 to use it. More importantly for testing, the server must bind the authorization code to the original challenge—not simply accept PKCE-shaped parameters.

3. Probe redirect_uri exact matching and open redirects

redirect_uri exact matching is a high-value negative test because callback weaknesses can turn a valid authorization response into code or token leakage.

Test the registered callback against variants such as:

  • Different scheme: http instead of https.
  • Different host, subdomain, port, path case, trailing slash, or encoded path separator.
  • Additional query parameters and fragments.
  • Look-alike hostnames such as client.example.evil.test.
  • A callback path that performs an internal open redirect.
  • A token exchange request with a redirect_uri different from the authorization request.

The expected result is rejection unless a variant is explicitly registered and intended. Avoid broad wildcard callback patterns for browser-based clients. The OWASP OAuth 2.0 Cheat Sheet also recommends preventing arbitrary browser forwarding and requiring Resource Servers to enforce token-to-resource authorization.

4. Validate OIDC discovery, JWKS, and JWTs as separate controls

OpenID Connect (OIDC) Core adds identity assertions to OAuth. OAuth/OIDC security testing for implementers should test discovery and token validation independently because a correct signature check alone does not prove that a token belongs to the current client or issuer.

For OIDC discovery and JWKS:

  1. Fetch /.well-known/openid-configuration only from the configured issuer over HTTPS.
  2. Verify that the metadata issuer exactly matches the issuer you configured; do not silently follow an issuer change.
  3. Confirm that authorization_endpoint, token_endpoint, and jwks_uri come from trusted metadata, not from browser-controlled parameters.
  4. Rotate a signing key in the test environment and verify that cached JWKS data refreshes safely when a new known kid appears.
  5. Reject unexpected key sources such as a token-supplied jku or x5u URL unless the deployment has an explicitly designed, verified trust model.

For JWT validation (iss/aud/signature alg allowlist):

  • Require an exact iss match.
  • Require the intended client ID or API identifier in aud; validate azp where the OIDC profile requires it.
  • Verify the signature with a trusted JWKS key that matches the expected algorithm.
  • Configure an algorithm allowlist, such as RS256 or ES256 where appropriate; never select an algorithm solely because an untrusted JWT header requests it.
  • Validate time-based claims (exp, nbf, and iat) with a small documented clock-skew allowance.
  • For an OIDC login, verify nonce, and verify the authorization-response binding requirements used by the application.

OpenID Connect Core requires ID Token signature validation and defines the iss, aud, and nonce claims used in these checks. In a survey of 137 sites using Google Sign-In, 69 had at least one serious OAuth 2.0 or OIDC security or privacy vulnerability[4].

5. Enforce Authorization Server and Resource Server boundaries

OAuth/OIDC security testing for implementers must test the API separately from login. A valid login does not automatically make a token valid for every API.

Run these tests at every Resource Server:

  • Present an access token minted for a different API audience.
  • Reduce or remove a required scope, then call a sensitive route.
  • Use a token belonging to User A to access User B’s object identifier.
  • Try an ID Token as an API bearer token; the Resource Server should reject it unless the architecture explicitly defines that profile.
  • Try an opaque token where a JWT is expected, and a JWT where introspection is required.
  • Revoke or expire a token and confirm that the Resource Server stops accepting it according to the deployment’s validation or introspection model.

When an Authorization Server issues JWT access tokens, Resource Servers should validate them locally against the intended issuer, audience, signature, algorithm policy, expiry, and authorization claims. When an Authorization Server issues opaque tokens, Resource Servers should use the approved introspection or gateway path rather than guessing at token contents.

6. Use negative testing and fuzzing of parameters

Negative testing and fuzzing of parameters should be structured, rate-limited, and repeatable. Start with a single mutation per request so that a failure is explainable, then combine mutations after individual controls are proven.

Prioritize these inputs:

  • client_id, response_type, scope, state, nonce, code_challenge, and code_challenge_method at the authorization endpoint.
  • grant_type, code, redirect_uri, client_assertion, and code_verifier at the token endpoint.
  • Duplicate parameters, missing parameters, empty values, percent encoding, Unicode normalization, extremely long values, repeated keys, and mixed query/body copies.
  • JWT header fields including alg, kid, typ, jku, and x5u.

Success criteria are explicit: reject malformed or unauthorized input, avoid verbose error disclosure, issue no credential, create an audit event without secrets, and remain available. Tools such as Burp Suite and OWASP ZAP can help mutate requests and replay controlled flows; protocol-aware automated tests remain necessary to check transaction binding across multiple steps.

Turn OAuth/OIDC security testing for implementers into release gates

OAuth/OIDC security testing for implementers is most effective when every confirmed negative test becomes a regression test. A practical release gate includes:

  1. A passing Authorization Code Grant with PKCE and scoped access.
  2. Rejection of missing, altered, reused, and cross-session state values.
  3. Rejection of altered, missing, reused, and downgraded PKCE verifiers.
  4. Exact callback validation, including rejection of open-redirect chains.
  5. OIDC discovery issuer verification and safe JWKS refresh behavior.
  6. JWT rejection tests for wrong issuer, audience, key, signature, algorithm, expiry, and nonce.
  7. Resource Server tests for wrong audience, insufficient scope, revoked tokens, and cross-user object access.
  8. Redacted traffic evidence and logs demonstrating expected failures.

Keep the resulting test cases close to the implementation. A framework upgrade, identity-provider change, new callback domain, gateway migration, or new mobile client can change the security properties of the same nominal OAuth/OIDC flow.
