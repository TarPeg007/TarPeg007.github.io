How to Reliably Identify BOLA in Real APIs

Broken Object Level Authorization (BOLA) vulnerability identification is reliable only when you test the same API object with at least two authorized identities, altered identifiers, and both read and write operations. Build a permission matrix, run controlled negative tests, inspect every resolver or data-access path, and verify that unauthorized requests consistently fail without leaking data.

BOLA is the API form of an access-control failure often called IDOR (Insecure Direct Object Reference). Authentication can be correct while authorization is wrong: a valid user token reaches an endpoint, supplies another customer’s order ID, invoice ID, document ID, or tenant ID, and the server returns or changes the object without proving that the requester may use that specific object. The OWASP API Security Top 10 lists BOLA as API1:2023.

What reliable BOLA vulnerability identification tests

Broken Object Level Authorization vulnerability identification should test the authorization decision for the object, not merely whether a caller can reach an endpoint. A successful 200 OK response is not proof that authorization worked; it may show only that the API accepted a valid token.

The Wallarm API ThreatStat 2026 report places BOLA at 39% of its OWASP API Top 10 vulnerability distribution.[1] An Edgescan analysis of critical and high-risk API findings recorded BOLA at 15.0% of the issues in its reviewed API dataset.[2] These reports use different datasets and methodologies, so their percentages should not be combined. They support the same operational conclusion: object-level authorization deserves explicit testing.

Use this distinction when preparing API authorization tests / negative testing:

Test question Secure expected result BOLA indicator
Can User A read User B’s object? 403, 404, or an equivalent policy-safe denial User B’s data is returned
Can User A modify or delete User B’s object? Request is denied and the object remains unchanged State changes on User B’s object
Can a user cross tenant boundaries? Tenant isolation / multi-tenancy controls deny access A different tenant’s record is exposed or changed
Can a lower-privilege user act on an admin-owned object? Role and object policy both deny the request The action succeeds through a valid endpoint

A recent empirical taxonomy fully classified 107 public bug-bounty reports tagged for IDOR or improper access control.[3] In a related analysis of confirmed cases, action-level BOLA—unauthorized updates, deletions, or other state changes—accounted for 41.7% of cases.[4] Therefore, a read-only check is insufficient: test POST, PUT, PATCH, and DELETE flows as deliberately as GET flows.

A repeatable process for finding BOLA in real APIs

Perform testing only on systems you own or are explicitly authorized to assess. Keep the test data synthetic where possible, minimize access to other users’ records, and record evidence without unnecessarily retaining sensitive responses.

  1. Create distinct test identities and objects.

    • Create User A and User B in the same role and, for multi-tenant systems, Tenant A and Tenant B.
    • Create objects owned by each identity: orders, profiles, documents, tickets, payment methods, API keys, or workflow records.
    • Add a lower-privilege identity and an administrator identity where the application supports privileged workflows.

  2. Map every object reference.

    • Review URL path values such as /orders/{orderId}.
    • Review query values such as ?accountId= or ?tenantId=.
    • Review JSON and form fields, headers, cookies, bulk-operation arrays, file references, and opaque cursor values.
    • Include indirect references discovered through list, search, export, notification, and webhook endpoints.

  3. Build an authorization matrix before sending tests.

    • Define the subject: User A, User B, support user, service account, or administrator.
    • Define the object: owned object, peer object, cross-tenant object, shared object, deleted object, and privileged object.
    • Define the action: read, create, update, delete, download, approve, invite, transfer, or execute.
    • Define the required outcome: allowed, denied, filtered, or redacted.

  4. Run paired requests, not one-off tampering.

    • First send a known-valid request as User A against User A’s object.
    • Repeat the same request with only the object reference changed to User B’s object.
    • Compare HTTP status, response body, response size, side effects, audit events, and later retrieval of the target object.
    • Repeat the pair with a cross-tenant target to validate tenant isolation / multi-tenancy controls.

  5. Test negative cases across all HTTP methods.

    • Test reads, exports, downloads, previews, and search filters.
    • Test writes, especially partial updates, bulk actions, ownership reassignment, invitation flows, and deletion.
    • Test asynchronous actions such as queued exports, background jobs, webhook replays, and approval links.
    • Treat an error-message data leak, a different response shape, or a timing difference as a lead for manual review—not automatic proof of BOLA.

  6. Validate the server-side policy path.

    • Verify that the API derives ownership and tenant context from trusted server-side state rather than from a client-supplied userId or tenantId.
    • Verify authorization immediately before the data query or mutation, including alternate endpoints that reach the same service or repository.
    • Confirm that caching, CDN keys, background workers, and object storage signed URLs do not bypass the same policy.

The OWASP Testing Guide BOLA procedure recommends altering object identifiers and verifying whether another user’s data or actions become available. For test planning, NIST SP 800-115 provides a broader framework for scoping technical tests, collecting evidence, and turning findings into remediation work.

How RBAC, ABAC, GraphQL, and tenant controls affect BOLA tests

RBAC (Role-Based Access Control) answers whether a role may call a capability, such as whether a support agent may access a case-management endpoint. RBAC alone does not guarantee that the support agent may access every case returned by that endpoint.

ABAC (Attribute-Based Access Control) evaluates contextual attributes such as object owner, tenant, project membership, region, classification, device posture, or relationship to the record. ABAC can express object-level policy more precisely, but Broken Object Level Authorization vulnerability identification must still prove that the policy is enforced consistently in each data-access path.

Use these checks to avoid common blind spots:

  • RBAC check: use a lower-privilege token against an administrator-only operation. This primarily detects broken function-level authorization.
  • Object-ownership check: use a peer’s identifier with a role that is otherwise allowed to call the endpoint. This detects classic horizontal BOLA or IDOR.
  • ABAC check: change the project, subscription, region, sharing state, or account relationship while keeping the API action constant.
  • Tenant-isolation check: use a valid object ID from another tenant and verify that every retrieval, mutation, export, and indirect lookup denies access.
  • Lifecycle check: test newly created, transferred, archived, restored, and soft-deleted objects. Authorization bugs often appear when ownership or tenant attributes change.

GraphQL resolvers authorization needs the same discipline. Do not assume authorization at the top-level query protects nested fields, node(id: ...) lookups, mutations, batch queries, or subscriptions. For GraphQL, test a legitimate query as User A, substitute User B’s global ID or nested relationship, and inspect every resolver path that returns or mutates an object. The OWASP GraphQL Cheat Sheet specifically calls out broken authorization, including IDOR-style excessive access.

How to confirm, report, and fix a BOLA finding

A reliable finding contains a minimal, reproducible authorization bypass—not a claim based only on predictable IDs. UUIDs and opaque identifiers can make enumeration harder, but they do not replace an authorization decision.

Document the finding with:

  1. The authorized test scope and environment.
  2. The two identities, roles, and tenant relationships used.
  3. A baseline request that legitimately accesses User A’s object.
  4. A minimally changed request that accesses or changes User B’s object.
  5. The observed response and any confirmed state change.
  6. The expected policy rule, such as “a user may update only documents owned by the same tenant and project.”
  7. The remediation location: middleware, service-layer policy, repository query predicate, resolver, worker, or storage authorization layer.
  8. A regression test that proves both the permitted and denied cases.

The preferred fix is an enforceable server-side rule that binds the authenticated principal, object, action, and tenant context before data is returned or changed. Add regression tests for peer-object, cross-tenant, and privileged-object denials. Re-run the same paired API authorization tests / negative testing after deployment and after any change to sharing, migration, caching, or GraphQL resolver logic.
