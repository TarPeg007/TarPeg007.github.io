How to Test Web Apps for IDOR With Repeatable Steps

IDOR (Broken Object Level Authorization) testing should prove that every server-side object action is denied unless the authenticated user, tenant, role, and policy allow it. Build an authorization matrix, replay authorized requests through an intercepting proxy, change one object reference at a time, test safe negative controls, and preserve evidence for regression testing.

Why IDOR (Broken Object Level Authorization) testing needs a repeatable method

IDOR is an authorization flaw in which a user can access or act on an object by changing a client-controlled reference—such as an order ID, document UUID, account number, GraphQL node ID, filename, or API path parameter. In API terminology, OWASP calls the same core problem BOLA (Broken Object Level Authorization). Authentication confirms who made the request; IDOR (Broken Object Level Authorization) testing verifies whether that identity is allowed to act on the specific target object.

IDOR belongs within Broken Access Control (OWASP Top 10), which OWASP retained as A01 in 2025. OWASP’s contributed dataset found that 3.73% of tested applications had at least one Broken Access Control weakness.[1] In OWASP’s 2021 contributed dataset, Broken Access Control recorded 318,487 occurrences.[2] On the HackerOne platform, IDOR accounted for 7% of reported vulnerabilities in the cited report.[3] HackerOne also reported that valid IDOR reports rose 29% from 2024 to 2025.[4]

Use the OWASP API Security Top 10 guidance for BOLA to distinguish object-level authorization from endpoint-level authorization. A standard user reaching an administrator-only endpoint is usually a function-level authorization issue; a permitted endpoint returning another tenant’s invoice is an IDOR/BOLA issue.

Test element What to vary Expected secure result
Object ownership Replace an owned object ID with a different tenant’s test object ID Server denies access without returning protected data
Role Replay the same request as a lower-privilege role Server denies actions outside assigned permissions
Tenant or organization Keep role constant and switch organization context Server enforces tenant isolation
HTTP method or action Change read to update, delete, export, approve, or share Server evaluates authorization for the requested action
Object state Target draft, archived, locked, or pending-approval records Server enforces workflow and policy constraints

Repeatable IDOR (Broken Object Level Authorization) testing steps

Perform IDOR (Broken Object Level Authorization) testing only with written authorization, a defined Rules of Engagement, dedicated accounts, and synthetic data where possible. Rate limiting / safe testing controls should set request ceilings, testing windows, escalation contacts, and stop conditions before any request manipulation begins.

  1. Map objects, actions, and trust boundaries.

    • List every object exposed through routes, query strings, request bodies, GraphQL variables, file paths, exports, webhook callbacks, and background-job references.
    • Record meaningful actions: create, read, update, delete, download, export, approve, invite, refund, assign, and administer.
    • Include browser workflows, REST endpoints, GraphQL operations, mobile backends, and undocumented endpoints observed in authorized traffic.

  2. Build an authorization matrix before sending altered requests.

    • Create at least two test tenants and multiple identities: anonymous, standard user, manager, support user, and administrator where applicable.
    • Define the expected allow or deny decision for each object/action combination.
    • Cover Role-Based Access Control (RBAC) rules, such as whether a manager can approve a request, and Attribute-Based Access Control (ABAC) / policy enforcement rules, such as region, account status, project membership, subscription, or record lifecycle state.

  3. Capture a known-good request with an intercepting proxy.

    • Use an Intercepting proxy such as Burp Suite, OWASP ZAP, or Caido to capture a request that legitimately accesses an object owned by the current test account.
    • Save the complete baseline: authenticated identity, tenant context, HTTP method, endpoint, request headers, body, object reference, response code, and response body.
    • Do not begin by guessing identifiers at scale. A controlled baseline makes results reproducible and reduces unnecessary traffic.

  4. Change one authorization input at a time.

    • Replace only the target object reference with an object belonging to the second test tenant.
    • Repeat the request without changing the session, role, method, or payload.
    • Then test a controlled variation: same object with a lower-privilege role, a different tenant header or organization selector, or a state-changing method.
    • Treat a 200 OK, leaked metadata, successful download, or accepted state change for an unauthorized object as a finding candidate. Do not rely only on status codes; inspect response length, fields, side effects, and audit logs.

  5. Run negative controls to avoid false positives.

    • Use Negative controls (non-existent/same-owner objects) alongside the cross-owner test.
    • A same-owner object should succeed when the baseline says it should.
    • A non-existent object should follow the application’s normal missing-object behavior.
    • A cross-tenant object must be denied consistently. If a supposedly denied request changes state asynchronously, verify the target object afterward with the authorized owner account.

  6. Test the full action set, not only GET.

    • IDOR (Broken Object Level Authorization) testing must include read, update, delete, download, export, share, bulk action, approval, and workflow-transition requests.
    • Test direct API calls as well as user-interface controls. Hiding a button in the browser does not enforce authorization on the server.
    • Check nested references too: /projects/{projectId}/files/{fileId}, invoice line items, attachments, comments, saved searches, reports, and generated exports often have separate authorization paths.

  7. Record proof that engineering can replay safely.

    • Preserve the precondition, test identity, tenant, endpoint, sanitized request, changed field, observed response, expected result, actual result, affected build, and timestamp.
    • Limit proof of impact to the minimum necessary. A redacted title, object identifier, or harmless synthetic record is often enough to demonstrate cross-tenant access.
    • Map the issue to the authorization rule that failed rather than describing the identifier format as the root cause.

Fixing IDOR (Broken Object Level Authorization) findings and preventing recurrence

A UUID, opaque identifier, encrypted ID, or random slug can make enumeration more difficult, but it does not replace an authorization decision. IDOR (Broken Object Level Authorization) is fixed when the server checks whether the authenticated principal may perform the requested action on the requested object under the current policy.

Use these remediation priorities:

  1. Move decisions to centralized authorization middleware / policy layer where practical.

    • Centralized authorization middleware / policy layer logic reduces the chance that one controller, resolver, worker, or export endpoint skips an ownership check.
    • Keep domain-specific checks close enough to the data and business operation that background jobs and alternate API paths cannot bypass them.

  2. Enforce deny-by-default and object-aware decisions.

    • Scope database queries by tenant and authorized subject where feasible.
    • Evaluate object ownership, membership, delegated access, role, state, and applicable ABAC attributes on every sensitive action.
    • Avoid trusting tenant IDs, user IDs, role flags, or access-control claims supplied solely by the client.

  3. Test authorization controls through regression testing for security fixes.

    • Convert the confirmed proof of concept into an automated integration or API test.
    • Include allow cases, cross-tenant deny cases, lower-role deny cases, and non-existent-object controls.
    • Re-run the test whenever authorization middleware, routing, ORM scopes, token claims, tenant switching, GraphQL resolvers, or business workflows change.

  4. Add monitoring without exposing sensitive records.

    • Log denied authorization events with correlation IDs, endpoint, action, and policy result.
    • Alert on repeated cross-tenant denials or unexpected authorization failures, but avoid logging full secrets, tokens, or protected payloads.

A useful completion criterion for IDOR (Broken Object Level Authorization) testing is simple: every row in the authorization matrix has an expected decision, a captured result, a safe negative control, and—where a fix was made—a passing regression test.
