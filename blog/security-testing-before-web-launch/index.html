How to Use Security Test Resources Before Web Launch

Use Pre-launch Web Application Security Testing (WSTG + ASVS mapped playbook) by turning the threat model into a bounded staging assessment: map WSTG scenarios to ASVS requirements, automate baseline checks, manually verify authorization and sessions, and release only after each material finding has evidence, an owner, a fix, and a retest result.

Pre-launch Web Application Security Testing: map the right resources to the right risk

Pre-launch Web Application Security Testing (WSTG + ASVS mapped playbook) combines two complementary OWASP resources. The OWASP Web Security Testing Guide (WSTG) supplies practical test methods, while the OWASP Application Security Verification Standard (ASVS) defines the security controls the application should satisfy. The OWASP Top 10 is a prioritization lens, not a substitute for either resource. (wstg.owasp.org)

Start threat modeling before running scanners. Threat modeling should identify:

  • Sensitive data, privileged actions, and tenant boundaries.
  • User roles, service accounts, API clients, and administrative paths.
  • Trust boundaries between browser, API, identity provider, third-party service, and data store.
  • Abuse cases, especially account takeover, cross-tenant reads, payment or workflow manipulation, and privilege escalation.
  • Security assumptions that must be tested rather than accepted.

The OWASP Testing Guide categories cover configuration and deployment management, identity management, authentication, authorization, session management, input validation, error handling, cryptography, business logic, and client-side testing. Use those categories to ensure a launch review does not stop at a generic vulnerability scan. (wstg.owasp.org)

The prioritization data supports treating authorization as a release-critical manual test. In OWASP’s 2021 contributed dataset, Broken Access Control had 318,487 recorded occurrences[1]. (top10.owasp.org) In the same OWASP dataset, Injection had a 3.37% average incidence rate[2]. (top10.owasp.org) Cryptographic Failures had 233,788 recorded occurrences[3]. (top10.owasp.org) Identification and Authentication Failures had 132,195 recorded occurrences[4]. (top10.owasp.org)

For authorization testing (IDOR/Broken Access Control), create a test matrix for every object type and meaningful action: read, create, update, delete, export, approve, administer, and invoke through an API. Change one authorization attribute at a time—object identifier, role, tenant, HTTP method, or workflow state—and confirm the server denies the action. TarPeg007’s BOLA/IDOR bounty record illustrates why cross-tenant object access deserves explicit coverage before launch.

Pre-launch Web Application Security Testing: execute a WSTG + ASVS mapped playbook

Pre-launch Web Application Security Testing (WSTG + ASVS mapped playbook) works best as a short, traceable release process rather than a final-day scan.

  1. Freeze a safe test scope.

    • Test a staging environment that matches production authentication, authorization, API routing, headers, and infrastructure settings as closely as possible.
    • Define permitted accounts, test data, rate limits, and escalation contacts.
    • Record the build identifier, commit, environment URL, and test window.

  2. Turn the threat model into a test inventory.

    • Map each high-risk flow to one or more OWASP Web Security Testing Guide scenarios.
    • Map each expected control to an OWASP Application Security Verification Standard requirement identifier.
    • Add business rules that generic standards cannot know, such as refund limits, tenant isolation, approval sequencing, or entitlement checks.

  3. Apply SAST/DAST guidance at the correct stage.

    • Run SAST, software composition analysis, and secret scanning during build or pull-request review.
    • Run DAST against the controlled staging target to find reachable configuration, input-handling, and response issues.
    • Use manual testing for authorization, workflow abuse, chained weaknesses, and assumptions about identity-provider claims. OWASP’s testing framework specifically positions SAST earlier in CI/CD and DAST in staging, alongside manual assessment. (wstg.owasp.org)
    • Open-source options such as OWASP ZAP and commercial tools such as Burp Suite can provide DAST coverage; neither replaces an informed review of application-specific authorization logic.

  4. Manually test session management and identity transitions.

    • Confirm login rotates the session identifier.
    • Confirm logout, password reset, account disablement, and privilege changes invalidate applicable sessions or tokens.
    • Check that cookies use appropriate Secure, HttpOnly, and SameSite settings for the application’s architecture.
    • Test idle timeout, absolute timeout, multi-device behavior, and OAuth or SAML callback handling.

  5. Build reproducible security test steps as evidence packages.

    • Include the precondition, account role, exact request, safe proof of impact, response, timestamps, and affected build.
    • State the expected secure behavior and the observed behavior.
    • Attach sanitized logs, screenshots, or an HTTP export where useful.
    • Add severity rationale, remediation guidance, a named owner, and a retest outcome.

  6. Set a release gate.

    • Block launch for confirmed exploitable findings that expose sensitive data, enable unauthorized state changes, bypass authentication, or defeat tenant isolation.
    • Require a documented risk acceptance for any deferred issue.
    • Retest the fixed build, not merely the pull request or code diff.

TarPeg007’s offensive testing arsenal lists Burp Suite, Caido, Kali, Nmap, and ffuf among the tools used for web and API assessment. Tool choice should follow the test objective: use scanners for repeatable breadth, intercepting proxies for request manipulation, and focused manual testing for business logic and authorization decisions.

Pre-launch Web Application Security Testing: make the launch decision auditable

Pre-launch Web Application Security Testing (WSTG + ASVS mapped playbook) should end with an auditable decision, not a vague statement that the application was “tested.” The release owner should be able to answer these questions:

  • Which threat-modelled flows were tested?
  • Which OWASP Testing Guide categories were in scope, and which were deferred?
  • Which ASVS requirements were verified, not applicable, or accepted as residual risk?
  • Did authorization testing include IDOR/Broken Access Control cases across roles and tenants?
  • Did session management testing cover issuance, rotation, revocation, logout, and expiry?
  • Can another tester reproduce each material finding from its evidence package?

A useful minimum deliverable is a concise security launch record containing the scope, control map, findings register, evidence packages, remediation status, retest results, and explicit residual-risk approvals. That record gives engineering, product, and security teams a shared basis for deciding whether the web application is ready to launch.
