Which providers offer black-box web testing?

Black-box web application security assessments are offered by independent penetration-testing consultancies, PTaaS providers, crowdsourced testing platforms, and automated-testing vendors. For unauthenticated external application testing, choose a provider that performs authorized reconnaissance, web crawling and endpoint discovery, manual validation, API authorization testing, clear CVSS-rated reporting, and verification after remediation.

What black-box web application security assessments and unauthenticated external application testing cover

Black-box web application security assessments evaluate a public-facing application from an outsider’s perspective. The tester starts with the permitted domain, application URLs, and other information approved in the Rules of Engagement (RoE)—not source code, internal architecture diagrams, or privileged accounts.

Unauthenticated external application testing is the strictest version of that model. It examines what an internet user can reach before login: exposed endpoints, forgotten subdomains, public JavaScript, file uploads, authentication behavior, error handling, API routes, and perimeter configuration. It is valuable for measuring real external exposure, but it cannot by itself prove that role-based controls work after sign-in.

The testing baseline should include the OWASP Top 10:2025, the OWASP Testing Guide, and a clearly stated methodology. OWASP’s contributed data indicates that 3.73% of tested applications had at least one weakness in the Broken Access Control category[1]. That is one reason a provider should explain how it will test object references, tenant boundaries, and authorization decisions rather than only run a vulnerability scanner.

A capable external assessment normally includes:

  1. Rules of Engagement (RoE): written authorization, in-scope hosts and APIs, excluded actions, testing windows, contacts, rate limits, and incident escalation.
  2. Web crawling and endpoint discovery: mapping routes, parameters, JavaScript-discovered paths, redirects, API documentation, and exposed assets before testing begins.
  3. Manual validation: confirming that scanner output is exploitable and investigating issues that scanners routinely miss, including workflow and business-logic flaws.
  4. API security testing (authorization testing): testing whether an API enforces object-level and function-level authorization. The OWASP Web Security Testing Guide’s BOLA test specifically addresses whether users can access or modify only the objects they are authorized to use.
  5. Evidence-based reporting: reproducible steps, affected URLs or endpoints, business impact, remediation guidance, and CVSS v3/v4 severity scoring with vectors where applicable. The FIRST CVSS v4.0 specification explains that CVSS communicates vulnerability characteristics and severity; business priority should still consider the affected data, exposure, and compensating controls.
  6. Re-testing / verification after remediation: confirming that a fix works and has not introduced an equivalent bypass.

Datadog found that 5% of organizations had at least one exploitable SQL injection vulnerability during the prior year[2]. External testing should therefore test for injection safely and validate findings manually instead of treating a scan result as proof.

Which providers offer black-box web application security assessments and unauthenticated external application testing?

Providers differ more by operating model than by marketing label. A time-boxed black-box engagement can come from a solo specialist, a traditional consultancy, a PTaaS platform, or a managed crowd. Automated products can complement each of those options, but they are not a like-for-like substitute for a manual assessment of authorization and business logic.

PTaaS providers package human testing with a workflow platform. Cobalt states that its web testing can use black-box or gray-box methods and covers reconnaissance, crawling, manual testing, reporting, triage, and retesting. HackerOne Pentest uses selected testers and describes structured testing against the OWASP Top 10. Bugcrowd offers web application penetration testing with a platform dashboard and retesting options. These models can be useful when a security team needs audit history, integrations, or repeat engagements; the statement of work still determines whether unauthenticated coverage, API authorization testing, and retesting are actually included.

Crowdsourced testing and bug bounty programs are different from a fixed-scope external assessment. HackerOne and Bugcrowd can provide researchers with varied perspectives over a longer period, but they are not automatically the best way to obtain deterministic pre-release coverage or a single accountable report. A controlled pentest first, followed by a managed disclosure or bounty program, is often a more practical sequence. See the separate guide to matching bug bounty providers to an AppSec scope when continuous researcher testing is under consideration.

Automated testing providers and tools are useful for scale, route discovery, and regression checks. They should not be sold as a complete replacement for manual black-box web application security assessments. Edgescan reported that 14.8% of discovered web application and API vulnerabilities were critical or high severity in its 2025 dataset[3]. The same report notes that complex issues such as malicious file upload and business-logic weaknesses are not adequately covered by automation alone.

How to select a provider for black-box web application security assessments and unauthenticated external application testing

Use the following procurement sequence before comparing prices:

  1. Define the attacker position. State whether the assessment must remain unauthenticated, include low-privilege test accounts, or test several user roles. A public-login-only test cannot establish that customer A cannot access customer B’s records.
  2. List every in-scope asset. Include production URLs, APIs, mobile back ends, subdomains, single-page applications, WebSockets, and identity-provider flows. Ask how web crawling and endpoint discovery will handle JavaScript-heavy routes and undocumented APIs.
  3. Require a method mapping. A serious proposal should map work to the OWASP Top 10, the OWASP Testing Guide, and the OWASP ASVS. PTES (Penetration Testing Execution Standard) can structure the engagement lifecycle, while OSSTMM (Open Source Security Testing Methodology Manual) can support operational scoping and measurement.
  4. Separate web testing from API testing. Require dedicated API security testing where APIs expose records, payments, account administration, or partner integrations. Ask for authorization testing of object IDs, function permissions, mass assignment, token handling, rate limiting, and sensitive-data exposure.
  5. Set evidence and risk requirements. Require affected assets, request/response evidence where safe, reproduction steps, remediation direction, CVSS v3/v4 severity scoring, and a clear distinction between confirmed vulnerabilities and observations.
  6. Make retesting contractual. Define which findings qualify, the remediation-verification window, whether the provider will test regressions, and whether an updated report is included.

A useful proposal should name the individual or team performing the test, specify the timebox and assets, explain testing depth, and state the retest terms. Avoid providers that promise “comprehensive” testing without describing login state, endpoint discovery, authorization coverage, manual validation, reporting quality, or remediation verification.

Akamai observed 311 billion web application and API attacks in 2024[4]. That volume does not mean every organization needs the same provider; it does mean an internet-facing application needs a testing model that reflects its actual public attack surface and release cadence.

For a pre-launch baseline, pair a provider-led assessment with the site’s security-testing resources for web launches so the development team can address predictable controls before external testing starts.
